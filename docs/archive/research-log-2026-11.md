# Research facts gathered 2026-11-07 for the Touchline HLD (status: verified/likely/contradicted)

- [verified] (Instagram Basic Display API) Instagram Basic Display API reached end-of-life on December 4, 2024. Meta's words: "all Instagram Basic Display API requests will fail from that day onwards." No Instagram API for consumer (personal-account) apps remains. Meta pointed users to Instagram API with Facebook Login or with Instagram Login. => The HLD must not mention Basic Display. The podcast's Instagram must be a professional (Business or Creator) account, and Phase 2 must use a Graph-based Instagram API. [src: https://developers.facebook.com/blog/post/2024/09/04/update-on-instagram-basic-display-api/]
- [verified] (Instagram API setups (Nov 2026)) There are three setups. Unified Login ("recommended for new integrations"): graph.facebook.com, Business Integration System User token, no Facebook Page needed. Instagram Login: graph.instagram.com, Instagram User token, no Page. Facebook Login: graph.facebook.com, User/Page token, Instagram account must be linked to a Page. All three need an Instagram professional account. => Show Unified Login (graph.facebook.com) as the Instagram integration in the architecture diagram. Make the Meta host and version config-driven, not hard-coded. [src: https://developers.facebook.com/docs/instagram-platform/overview]
- [contradicted] (Instagram API with Instagram Login availability) Common belief: new apps should use Instagram API with Instagram Login (graph.instagram.com). Actual state: the migration guide says "Newly created apps can't set up the Instagram API with Instagram Login." Existing integrations keep working ("no end date yet"), but "New features ship only on the Instagram API with Unified Login." => Phase 2 must not plan around graph.instagram.com or the ig_refresh_token flow for a new app. Build the Instagram adapter on Unified Login, with Facebook Login for Business as the fallback. [src: https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/migration-guide.md]
- [verified] (Unified Login prerequisites and token) Needs a Meta app with the "Manage messaging & content on Instagram" use case, owned by a business portfolio, plus a Facebook Login for Business configuration. Exchanging the code at graph.facebook.com/v27.0/oauth/access_token returns a Business Integration System User token. Get the Instagram account ID from GET /me/assigned_instagram_accounts. Required permissions: instagram_basic and instagram_manage_messages. => Phase 2 steps: create the business portfolio, create the app with the use case, define the configuration, and have an admin do a one-time login to mint the token. The backend then stores the token server-side and calls only graph.facebook.com. [src: https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-unified-login/get-started]
- [verified] (Access levels / App Review for own assets) Standard Access is granted automatically, needs no App Review, and permissions "can only be requested from app users who have a role on the requesting app." The Instagram App Review page says "My app is only for a business I own or manage" means review is not required. Advanced Access needs App Review plus Business Verification. Serving other clients also needs Live mode. => If the podcast business owns the Instagram and Facebook assets and the admin has a role on the app, the HLD can plan with no App Review and no Business Verification. Flag this as an assumption to re-check if third-party accounts are added later. [src: https://developers.facebook.com/docs/graph-api/overview/access-levels ; https://developers.facebook.com/documentation/instagram-platform/app-review.md]
- [verified] (App modes) "Apps in Development mode can only request permissions from role users", and data created in Development mode is visible only to role users. Meta says to switch to Live only after development and App Review are done. Instagram webhooks need the app to be "published or Live". => A Development-mode app is fine for the Phase 2 localhost demo using admin-role accounts. Moving to Live (privacy policy URL, icon, category) belongs in Phase 3 readiness, and only matters if webhooks or Advanced Access are needed. [src: https://developers.facebook.com/docs/development/build-and-test/app-modes ; https://developers.facebook.com/documentation/instagram-platform/webhooks/setup]
- [verified] (System User tokens) Facebook Login for Business system-user tokens "Default to never expire". Setting set_token_expires_in_60_days=true (which Meta's system-user doc marks "Recommended") creates a 60-day expiring token that must be refreshed. A system user and the app must belong to the same business. Installing apps for system users needs Ads Management API standard access or above. => Keep Meta tokens in AWS Secrets Manager (or Render/Vercel env secrets), never in the SPA. If 60-day tokens are used, add a scheduled rotation job and an alert on error code 190 (invalid token). [src: https://developers.facebook.com/docs/facebook-login/facebook-login-for-business ; https://developers.facebook.com/docs/marketing-api/system-users/install-apps-and-generate-tokens]
- [verified] (Instagram Login token lifetimes (legacy apps)) Authorization code and short-lived token: 1 hour. Long-lived token: 60 days (expires_in 5184000), from GET graph.instagram.com/access_token?grant_type=ig_exchange_token with client_secret, server-side only. Refresh: GET graph.instagram.com/refresh_access_token?grant_type=ig_refresh_token. The token must be at least 24h old, unexpired, and have instagram_business_basic. A refreshed token lasts 60 days; one not refreshed within 60 days cannot be refreshed. => Mention this only as a legacy or fallback path. If it is used, a refresh cron (for example every 30 days) is mandatory, because missing the 60-day window breaks the integration. [src: https://developers.facebook.com/documentation/instagram-platform/reference/refresh_access_token.md ; https://developers.facebook.com/documentation/instagram-platform/reference/access_token.md]
- [verified] (Facebook Page access tokens) A long-lived User token "generally lasts about 60 days" and is obtained from GET oauth/access_token?grant_type=fb_exchange_token. A Page token taken from a long-lived User token via GET {user-id}/accounts: "Long-lived Page access token do not have an expiration date." => For the Facebook adapter, use a non-expiring Page token or a system-user token. Still handle invalidation (error 190), for example if the admin loses their role, by alerting and re-minting through a runbook. [src: https://developers.facebook.com/docs/facebook-login/guides/access-tokens/get-long-lived]
- [verified] (Instagram media listing endpoint) GET /{ig-user-id}/media "Returns a maximum of 10K of the most recently created media". Stories are excluded (use /stories). It supports time-based pagination (since/until, Unix timestamps). By default only id is returned, so fields must be requested. Facebook Login permissions: instagram_basic plus pages_read_engagement or pages_show_list, plus ads_management or business_management if the role came through Business Manager. => The Instagram adapter should always send an explicit fields= list, follow paging.next, and use since= for incremental sync. Stories are out of scope for the social feed. [src: https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user/media.md]
- [verified] (Instagram media fields) IG Media fields: id; media_type (CAROUSEL_ALBUM, IMAGE, VIDEO); media_url; thumbnail_url ("Only available on VIDEO media"); permalink; timestamp (ISO 8601 UTC); like_count; comments_count; username; shortcode; children edge. caption and media_product_type (AD, FEED, STORY, REELS) are annotated "Available for Instagram API with Facebook Login only." permalink cannot be used on album children. => Make caption, mediaProductType and the counts optional in the normalized SocialPost contract. Confirm caption availability for the chosen setup in Graph API Explorer during Phase 2. [src: https://developers.facebook.com/docs/instagram-platform/reference/instagram-media]
- [verified] (media_url omission and hidden likes) Since July 30, 2026, on all versions and both hosts, media_url is omitted when a video has copyrighted or licensed audio, is flagged for copyright, or the reel owner has disabled downloads. Docs: "Treat media_url as an optional field ... fall back to permalink or thumbnail_url." like_count is omitted through field expansion if the owner hides like counts. => The frontend social card must render with media_url missing, using the thumbnail plus a link to permalink, or an oEmbed. Do not plan to re-host or stream Instagram video from the backend. [src: https://developers.facebook.com/documentation/instagram-platform/changelog.md]
- [verified] (Instagram insights deprecations) On January 21, 2025, Meta deprecated the impressions (media and user), plays, clips_replays_count and ig_reels_aggregated_all_plays_count metrics: from v22.0, and on all versions from April 21, 2025. The new views metric replaces them. Insights became available to Instagram Login apps. On April 22, 2026, reposts_count, saved_count and shares_count were added (Facebook Login only). => Any engagement metrics in the API contract should use views, likes and comments counts, not impressions or plays. Insights need instagram_manage_insights, so keep them out of scope unless required. [src: https://developers.facebook.com/documentation/instagram-platform/changelog.md]
- [verified] (Facebook insights deprecations) v25.0 announced that impression-based Page, Post, Video and Story insights metrics would be deprecated on all versions when v26.0 was released (July 29, 2026). Examples: page_impressions_unique, page_posts_impressions, post_impressions_unique, post_video_views_unique, total_video_views_unique. Replacements: page_total_media_view_unique and post_total_media_view_unique. => The HLD should not promise impression or reach metrics for Facebook content. If view counts are shown, use the *_total_media_view_* metrics or skip insights entirely. [src: https://developers.facebook.com/docs/graph-api/changelog/version25.0]
- [verified] (Graph API latest version) The Graph API changelog says "The latest Graph API version is: v27.0", and current Instagram and Reels docs use v27.0 in their examples. The versions table still lists v26.0 (July 29, 2026, expiry TBD) as the newest dated entry, so v27.0's release date was not confirmed. v25.0 (Feb 18, 2026) runs until July 29, 2028. => Pin META_GRAPH_API_VERSION=v27.0 in config, with v26.0 as a fallback. Every Meta call should use the versioned path, and the backend should log the version in use. [src: https://developers.facebook.com/docs/graph-api/changelog ; https://developers.facebook.com/docs/graph-api/changelog/versions]
- [verified] (Graph API version lifecycle) "Each version is guaranteed to operate for at least two years." A version stops working two years after the next version is released. Calls to an expired version "will be defaulted to the next oldest, usable version." Unversioned calls use the version set in the App Dashboard. Meta releases a new version roughly every 4–5 months (Jan 2025, May 2025, Oct 2025, Feb 2026, Jul 2026). => Add a twice-yearly 'Meta API version bump' maintenance task to the Phase 3 operations runbook, with contract tests run against the new version before switching. [src: https://developers.facebook.com/docs/graph-api/guides/versioning]
- [verified] (Facebook Page posts endpoints) /{page-id}/feed includes Page posts, visitor posts and public posts tagging the Page, both published and unpublished (filter with is_published). Reading your own Page needs a Page token from a person with the CREATE_CONTENT, MANAGE or MODERATE task, plus pages_read_engagement and pages_read_user_content (and pages_show_list). Page Public Content Access is only for Pages you don't own. Returns about 600 ranked published posts per year; limit max 100. => Use /{page-id}/published_posts (own content only) with limit≤100 and cursor paging. Request pages_read_engagement, pages_read_user_content and pages_show_list. Page Public Content Access is not needed. [src: https://developers.facebook.com/docs/graph-api/reference/page/feed ; https://developers.facebook.com/docs/graph-api/reference/page/published_posts]
- [verified] (Facebook Page post fields) Post fields: id, message, created_time, permalink_url, full_picture, status_type, is_published, story, shares (a struct with count). Edges: attachments, reactions, likes, comments, sharedposts; use summary=true for total_count. The post endpoints "do not return Reels". The video `source` field is returned only for Page-owned videos when the requester is an admin. => Example query: fields=id,message,created_time,permalink_url,full_picture,attachments,shares,reactions.summary(total_count).limit(0),comments.summary(true).limit(0). Do not depend on `source`; link to permalink_url for playback. [src: https://developers.facebook.com/docs/graph-api/reference/page-post ; https://developers.facebook.com/docs/graph-api/reference/page/published_posts]
- [likely] (Facebook Page videos and Reels) GET /{page-id}/videos works with a Page token (MANAGE task) plus pages_read_engagement and returns id, description and updated_time by default. The Reels guide says GET /{page-id}/video_reels lists Page Reels (since/until supported; example uses v27.0), but the video_reels reference page says reading is unsupported. The Video node also has fields such as length, permalink_url, title and thumbnails. => Phase 2 should include a spike to confirm /videos and /video_reels field sets (length, permalink_url, picture/thumbnails) in Graph API Explorer before freezing the Episode/VideoClip contract. [src: https://developers.facebook.com/docs/video-api/guides/get-videos ; https://developers.facebook.com/docs/video-api/guides/reels-publishing ; memory (Video node fields)]
- [verified] (Rate limits (platform)) Platform rate limit for user/app tokens: calls within one hour = 200 × the app's unique daily active users. The X-App-Usage header returns call_count, total_cputime and total_time as percentages, and throttling may start at 100. Error codes: 4 (app), 17 (user), 32 (Pages user/app), 613 (custom limit). => The backend must never call Meta once per site visitor. Use a scheduled or cached aggregation (server-side TTL cache, Redis optional) so Meta call volume stays flat regardless of web traffic. [src: https://developers.facebook.com/docs/graph-api/overview/rate-limiting]
- [verified] (Rate limits (Business Use Case)) BUC limits for Pages with Page or system-user tokens: calls/24h = 4800 × engaged users. Instagram: calls/24h = 4800 × impressions in the last 24h. The X-Business-Use-Case-Usage header gives type (pages, instagram, and others), call_count, total_cputime, total_time and estimated_time_to_regain_access (minutes). Errors: 80001 (Pages), 80002 (Instagram). => The Meta client should parse both usage headers, emit them as metrics, back off when usage exceeds about 80%, honour estimated_time_to_regain_access, and serve stale cache on 4/17/32/613/80001/80002. [src: https://developers.facebook.com/docs/graph-api/overview/rate-limiting]
- [likely] (CDN media URL expiry) The media_url, thumbnail_url and full_picture values returned by Meta point to scontent*.cdninstagram.com or *.fbcdn.net. These URLs are signed (oh= parameter) and carry an expiry timestamp (oe=, hex Unix time). After expiry they return HTTP 403 ("URL signature expired"), typically within days. Meta's IG Media reference does not document a TTL. => Do not store CDN URLs as permanent data. Cache normalized social payloads with a short TTL (for example 15–60 minutes) and re-fetch from the Graph API. On image load errors, the frontend should fall back to permalink or a placeholder. [src: memory]

It needs App Review and "is only available with business verification". From November 3, 2025, author_name, author_url, thumbnail_url, thumbnail_width and thumbnail_height were removed from Facebook post, Facebook video and Instagram oEmbed responses, and the Facebook Page oEmbed endpoint was deprecated. => Do not build thumbnails from oEmbed. Embedding Facebook posts or videos through the oEmbed API brings in App Review and Business Verification, so prefer the backend's own normalized cards and link-outs. [src: https://developers.facebook.com/docs/features-reference/meta-oembed-read ; https://developers.facebook.com/documentation/instagram-platform/changelog.md]

Limit: 1,000 requests/hour. - [verified] (Meta Platform Terms (privacy, retention)) Platform Terms §4.a: maintain a privacy policy at a "publicly available, easily accessible ... non-geoblocked URL". §3.d.i: delete Platform Data on request, when it is no longer necessary for a legitimate business purpose, or when the service stops. Users need an easy way to request deletion. §3.a.iv bans selling or licensing Platform Data. §3.a.viii limits use to permitted purposes. => Phase 3 readiness must include a public /privacy page and a documented retention policy (for example, social cache purged after 24h with no long-term storage), and must not use Meta data for analytics resale. [src: https://developers.facebook.com/terms/dfc_platform_terms/]

App Review settings need a Privacy Policy URL, a 1024×1024 icon, a category and a business email. => The site has no end-user Meta login, so a static data-deletion instructions URL (for example /data-deletion) is enough. - [verified] (Data Use Checkup) Data Use Checkup is an annual assessment, required for apps "published live with a use case, or [with] advanced access to permissions or features". It is "not required for developers whose apps have Standard Access". It is needed to maintain API access, and has included data-handling questions since January 2024. => Add an annual Meta compliance task (Data Use Checkup, token and role audit) to the operations runbook if the app goes Live or gains Advanced Access. - [verified] (Instagram webhooks) Instagram webhook fields: comments, live_comments, mentions, messages, message_reactions, messaging_* fields, standby, story_insights. There is no field for newly published media. Requirements: app "published or Live", Advanced Access for comments and live_comments, and a public account. Subscribe with POST /{ig-account-id}/subscribed_apps and subscribed_fields. => Detect new Instagram posts by polling, for example a scheduled job every 10–15 minutes using since=. Webhooks are not a dependency for the social feed. [src: https://developers.facebook.com/documentation/instagram-platform/webhooks/fields ; https://developers.facebook.com/documentation/instagram-platform/webhooks/setup]
- [verified] (Page webhooks) The Page 'feed' webhook field "describes nearly all changes to a Page's feed". Item types include status, photo, video, share, comment and reaction; verbs include add, edited and remove. Ad posts are excluded, and Page-like notifications only come for Pages under 10K likes. It requires pages_manage_metadata granted by an admin with MODERATE and POST /{page-id}/subscribed_apps. The 'videos' field reports video encoding status. => The 'feed' webhook can be an optional Phase 3 add-on to invalidate the Facebook cache in near real time. Polling stays the baseline because Instagram has no equivalent. [src: https://developers.facebook.com/docs/graph-api/webhooks/reference/page]
- [verified] (Webhook endpoint requirements) The verification GET uses hub.mode=subscribe, hub.challenge and hub.verify_token. Payloads are signed in X-Hub-Signature-256 (HMAC-SHA256 with the app secret). A valid TLS certificate is required; self-signed certificates are not supported. Respond 200 OK; failed deliveries are retried for up to 36 hours. Meta switched its Webhooks mTLS CA on March 31, 2026 (meta-outbound-api-ca-2025-12.pem). => localhost (Phase 2) cannot receive webhooks without a tunnel (ngrok or cloudflared). Webhook handlers belong in Phase 3, behind ALB/App Runner TLS, with signature verification middleware and idempotent processing. [src: https://developers.facebook.com/docs/graph-api/webhooks/getting-started ; https://developers.facebook.com/docs/graph-api/changelog/version25.0]
- [verified] (Graph API pagination) Graph API supports cursor-based paging (before, after, paging.next), time-based paging (since, until) and offset paging (a last resort). Guidance: "Don't store cursors", "Stop paging when the next link no longer appears", and do not assume fewer results than limit means the end. Some edges cap limit. => The backend paging helper should follow paging.next until it is absent, with a hard max-pages guard. The BFF's own API should expose an opaque cursor that does not leak Meta cursors. [src: https://developers.facebook.com/docs/graph-api/results]
- [verified] (YouTube quota - default allocation and reset) Default allocation (granular system since 1 June 2026): 10,000 units/day shared by most endpoints, plus separate buckets of 100 search.list calls/day and 100 videos.insert calls/day. Invalid requests also cost quota (at least 1 unit). Daily quotas reset at midnight Pacific Time, which is 08:00 UK time most of the year (07:00 in the weeks when US and UK DST dates differ). => The BFF quota budget and alerting should use the 10,000-unit bucket. Reset quota counters and circuit breakers at midnight America/Los_Angeles, not at UK midnight. Count failed and retried calls in the budget. [src: https://developers.google.com/youtube/v3/determine_quota_cost ; https://developers.google.com/youtube/v3/getting-started#quota ; https://developers.google.com/youtube/v3/revision_history (1 June 2026)]
- [contradicted] (YouTube quota - search.list cost) CONTRADICTED belief that search.list costs 100 units: it now costs 1 unit in its own 'Search Queries' bucket, which is capped by default at 100 calls/day and does not draw on the 10,000-unit bucket. => Do not use search.list to list a channel's episodes; 100 calls/day is far too few. Reserve it for an optional, cached, rate-limited on-site search, and build listings from the uploads playlist. [src: https://developers.google.com/youtube/v3/docs/search/list ; https://developers.google.com/youtube/v3/determine_quota_cost]
- [verified] (YouTube quota - read method costs) channels.list, playlistItems.list and videos.list each cost 1 unit per call. The docs give fixed per-method costs and say nothing about cost varying with the parts requested; 'part' and 'fields' only reduce bandwidth and latency. => Request every needed part (snippet,contentDetails,statistics) in one call, and use 'fields' to trim payloads. Estimate cost per sync as calls x 1 unit. [src: https://developers.google.com/youtube/v3/determine_quota_cost ; https://developers.google.com/youtube/v3/getting-started]
- [verified] (YouTube - uploads playlist pattern) channels.list (by id, or by forHandle, which was added 31 Jan 2024) with part=contentDetails returns contentDetails.relatedPlaylists.uploads. playlistItems.list requires 'part', accepts maxResults 0-50 (default 5), and pages with nextPageToken/pageToken. Uploads playlist IDs are the channel ID with 'UC' replaced by 'UU' (confirmed empirically). => YouTubeService sync should resolve and cache the uploads playlist ID once, then page playlistItems.list with maxResults=50. A full re-sync of N videos costs about ceil(N/50) units plus the videos.list calls. [src: https://developers.google.com/youtube/v3/docs/channels ; https://developers.google.com/youtube/v3/docs/playlistItems/list ; https://developers.google.com/youtube/v3/revision_history]
- [likely] (YouTube - videos.list batching) videos.list takes 'id' as a comma-separated list and costs 1 unit. maxResults (1-50) cannot be combined with 'id'. The 50-IDs-per-call limit is widely enforced but is not stated on the current reference page. => Batch video detail lookups in chunks of at most 50 IDs. Handle a 400 error by splitting the batch. [src: https://developers.google.com/youtube/v3/docs/videos/list (id/maxResults verified); 50-ID cap from memory]
- [verified] (YouTube - new videos.batchGetStats method) New method since 3 June 2026: GET https://www.googleapis.com/youtube/v3/videos:batchGetStats with id plus part (contentDetails,id,snippet,statistics). It costs 1 unit in its own bucket (10,000 units/day by default), needs no auth for public videos, and returns viewCount, likeCount, commentCount, duration, durationMillis and a summary of failed IDs. => Use batchGetStats for periodic stats refreshes so they don't spend the main 10,000-unit bucket. durationMillis avoids parsing ISO 8601 durations. - [verified] (YouTube - API key vs OAuth) Google says to use an API key for requests that only retrieve public data, such as public video metadata or search results. OAuth 2.0 is required to insert, update or delete resources, or to read private user data (e.g. channels.list mine=true). => Phase 2 YouTube integration needs only a server-side API key held in the BFF (env var locally, Secrets Manager in production). No OAuth flow and no user login are needed for YouTube. [src: https://developers.google.com/youtube/registering_an_application]
- [verified] (Google API key restrictions) An API key can carry only one application-restriction type: HTTP referrers, IP addresses (external IPv4/IPv6/CIDR; internal IPs and localhost not supported), Android apps or iOS apps. API restrictions limit which APIs a key can call, and are mandatory when keys are created in the Console or gcloud. Google says unrestricted keys are insecure. => Use separate keys per environment, each restricted to the YouTube Data API v3. A production key restricted by IP needs static egress (NAT gateway with Elastic IP for App Runner VPC connector or ECS; Render static outbound IPs). Never ship the key to the React bundle. [src: https://docs.cloud.google.com/docs/authentication/api-keys]
- [verified] (YouTube - duration and timestamps) contentDetails.duration is an ISO 8601 duration (PT#M#S; PT#H#M#S; P#DT#H#M#S, e.g. PT15M33S) and may differ from playback by about 1 s. snippet.publishedAt is an ISO 8601 datetime. snippet.liveBroadcastContent is one of live, none or upcoming. => The normalizer should convert duration to integer seconds (durationSec) and publishedAt to UTC ISO strings. It should map liveBroadcastContent to an episode status (live/upcoming/published) and filter or badge live and upcoming items. [src: https://developers.google.com/youtube/v3/docs/videos]
- [verified] (YouTube - thumbnail keys and sizes) Video thumbnail sizes: default 120x90, medium 320x180, high 480x360, standard 640x480 (some videos) and maxres 1280x720 (some videos). Added 11 Sept 2026, for some videos: fhd 1920x1080, qhd 2560x1440, uhd 3840x2160. Channel thumbnails are 88x88, 240x240 and 800x800. => The Episode contract should expose a thumbnails map or array with width and height, picked by a fallback chain (maxres > standard > high > medium > default). The frontend can build srcset from it. Never assume maxres, fhd, qhd or uhd exist. [src: https://developers.google.com/youtube/v3/docs/videos ; https://developers.google.com/youtube/v3/revision_history (11 Sept 2026)]
- [verified] (YouTube - statistics fields) statistics returns viewCount, likeCount and commentCount. dislikeCount has been private since 13 Dec 2021 (owner-authorised requests only), and favoriteCount has been deprecated since 28 Aug 2015 (always 0). From 24 Aug 2026, viewCount counts views the moment a video starts playing, for long-form, Live and Shorts. => The contract should include viewCount, likeCount and commentCount only, all optional, because creators can hide likes and disable comments. Drop dislikes and favourites. Parse counts as numbers from the API's string values. [src: https://developers.google.com/youtube/v3/docs/videos]
- [verified] (YouTube - Shorts identification) The videos resource has no official field identifying a Short. Shorts can be up to 3 minutes; the YouTube Help page confirms this, and the 15 Oct 2024 effective date is from memory. Shorts are vertical or square, so a 'duration <= 180 s' rule also wrongly flags short horizontal clips. => Treat isShort as a heuristic and document it as such.
